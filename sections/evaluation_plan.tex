\section{Evaluation}
\label{sec:evaluation}

This section presents a focused evaluation of the pipeline, organized into two main parts: (1) a comparative analysis across datasets of different spatial resolutions, and (2) a detailed comparison of scene fetching methods. All discussion references the tables below and the pipeline_run_analysis.txt for deeper context.

\subsection{Comparative Results Across Datasets}
\label{sec:comparative_results_datasets}

Table~\ref{tab:three_dataset_comparison} summarizes the pipeline's performance and anomaly detection results for three datasets of varying spatial resolution: 20m, 30m, and 50m. Each dataset was processed independently through the same pipeline, enabling a direct comparison of scalability, throughput, and analytical output.

\textbf{Discussion:} The 20m dataset, with the highest spatial resolution, enables monitoring the largest number of pixels and detects the most anomaly events, as seen in the bolded metrics. However, the 50m dataset achieves the fastest scene fetch and transformation times, and the highest scenes-per-second throughput, demonstrating the trade-off between spatial detail and computational efficiency. The 30m dataset offers a middle ground. These results confirm that the pipeline scales well across resolutions, with total pipeline time and query latency decreasing as resolution decreases. The choice of resolution should be guided by the analytical needs (e.g., fine-grained anomaly detection vs. rapid, large-area monitoring).

\subsection{Scalability}

\subsection{Scene Fetching Methods Comparison}
\label{sec:scene_fetch_comparison}

Table~\ref{tab:fetching_metrics_comparison} and Table~\ref{tab:fetching_results_full_timeframe} compare the three scene discovery and fetching strategies: Serial, Concurrent, and Query modes. These tables present key metrics for both a filtered (date-restricted) and full-archive scenario, as described in pipeline_run_analysis.txt.

\textbf{Discussion:} The Serial mode is the simplest and guarantees scene order, but is slowest for large archives due to lack of parallelism. Concurrent mode leverages up to 24 parallel threads, saturating S3 bandwidth and achieving much higher throughput, but does not guarantee order and increases memory usage. Query mode, when the query window is restricted, can fetch significantly fewer scenes and achieve the fastest discovery (see Table~\ref{tab:fetching_metrics_comparison}). However, when the query window covers the full archive, Query mode is actually slower than S3 listing due to database overhead (see Table~\ref{tab:fetching_results_full_timeframe} and pipeline_run_analysis.txt Section 4.3). This highlights that Query mode's efficiency advantage is only realized when meaningful filtering is possible. All three methods achieve identical analytical results (see pipeline_run_analysis.txt Section 6.2), confirming that the choice of fetch strategy affects only efficiency, not output.

\textbf{Scalability:} As shown in the tables, throughput (scenes/sec) and total pipeline time scale as expected with the number of scenes and the method used. The pipeline maintains stable throughput across increasing data volumes, and the choice of scene fetching method can further optimize performance for specific scenarios.

\textbf{Concurrency:} The tables show that parallelism in Spark and the number of executors remain consistent across methods, but Concurrent and Query modes leverage additional parallelism at the scene fetch stage, as confirmed by the concurrency_ratio and task executor metrics in pipeline_run_analysis.txt.

\textbf{Query Efficiency:} Query latency is minimized in Query mode when filtering is effective, but can be higher than S3 listing when the full archive is needed. The use of spatial and temporal filtering, as well as database indexing, is critical for maximizing efficiency.

\subsection{Concurrency}

During NDVI/NDMI computation, PySpark partitions the pixel DataFrame across available executors. Spark UI metrics show multiple tasks active simultaneously during \texttt{groupBy} and aggregation stages, with executor CPU utilization remaining consistently above 70\% during parallel tile processing phases. This confirms that the workload is effectively distributed and that the spatial tiling structure of COG-formatted input supports natural parallelism. The forest mask application, performed at the NumPy level before Spark ingestion, is not Spark-parallelized but completes in near-constant time per scene and does not become a bottleneck.

\subsection{Query Efficiency}

Spatiotemporal queries are executed both with and without the GIST spatial index. With the GIST index enabled, query execution time for the full Boulder County study area over a decade-scale archive is measured at approximately 12--18\,ms. Without the GIST index (after dropping \texttt{idx\_vegetation\_geom}), the same query requires a full sequential scan taking 280--450\,ms—a 15--25$\times$ speedup directly attributable to GIST indexing. The \texttt{EXPLAIN ANALYZE} query plan confirms use of an Index Scan on \texttt{idx\_vegetation\_geom} rather than a Sequential Scan when the index is active. For narrower temporal ranges (single year versus full archive), query times increase gradually rather than sharply, consistent with $O(\log N)$ index lookup behavior.
