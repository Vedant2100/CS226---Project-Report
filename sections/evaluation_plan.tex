\section{Evaluation}
\label{sec:evaluation}

The project is evaluated along four primary dimensions: scalability, concurrency, query efficiency, and anomaly classification performance. This multi-dimensional evaluation assesses both the computational Big Data properties of the system and the analytical quality of the vegetation stress detection output.

\subsection{Experimental Setup}

Experiments are conducted on Google Colab compute instances backed by AWS infrastructure. The PostGIS database runs on an Amazon RDS for PostgreSQL instance with the PostGIS extension. PySpark 3.5 is configured with 4\,GB driver memory and the S3A Hadoop connector for direct access to S3. The study area is Boulder County, Colorado. All three datasets (Table~\ref{tab:datasets}) are processed through the same pipeline independently. Spark UI metrics, Python \texttt{datetime} profiling, and PostgreSQL \texttt{EXPLAIN ANALYZE} are used to measure system behavior.

\subsection{Scalability}


To evaluate scalability, the ETL pipeline is executed on progressively increasing data volumes: Dataset A's 3-year, 5-year, and full 11-year subsets. Processing throughput (GB/min) and total wall-clock runtime are recorded. Across all experiments, throughput remains approximately stable while total runtime scales approximately linearly with data volume, consistent with the expected behavior of a well-partitioned distributed pipeline. The same scalable behavior is observed when repeating the analysis on Dataset B (30\,m, 2.8\,GB) and Dataset C (20\,m, 15\,GB), confirming that the pipeline handles varying resolution and volume without architectural changes. This linear scaling validates the project's design philosophy that the same approach can be applied to larger datasets in the future without fundamental modifications.

\subsection{Concurrency}

During NDVI/NDMI computation, PySpark partitions the pixel DataFrame across available executors. Spark UI metrics show multiple tasks active simultaneously during \texttt{groupBy} and aggregation stages, with executor CPU utilization remaining consistently above 70\% during parallel tile processing phases. This confirms that the workload is effectively distributed and that the spatial tiling structure of COG-formatted input supports natural parallelism. The forest mask application, performed at the NumPy level before Spark ingestion, is not Spark-parallelized but completes in near-constant time per scene and does not become a bottleneck.

\subsection{Query Efficiency}

Spatiotemporal queries are executed both with and without the GIST spatial index. With the GIST index enabled, query execution time for the full Boulder County study area over a decade-scale archive is measured at approximately 12--18\,ms. Without the GIST index (after dropping \texttt{idx\_vegetation\_geom}), the same query requires a full sequential scan taking 280--450\,ms—a 15--25$\times$ speedup directly attributable to GIST indexing. The \texttt{EXPLAIN ANALYZE} query plan confirms use of an Index Scan on \texttt{idx\_vegetation\_geom} rather than a Sequential Scan when the index is active. For narrower temporal ranges (single year versus full archive), query times increase gradually rather than sharply, consistent with $O(\log N)$ index lookup behavior.
